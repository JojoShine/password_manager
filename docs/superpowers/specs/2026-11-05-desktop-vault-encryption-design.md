# Desktop vault encryption

Desktop macOS, Windows and Linux vaults use authenticated AES-256-GCM. The same master password unlocks the same copied/iCloud vault on another desktop; no device key is required. Web preferences and existing mobile storage are outside this change.

`VaultCrypto` derives a 32-byte key with PBKDF2-HMAC-SHA256 (600000 iterations), random 32-byte per-vault salt, on a worker isolate. Every write uses a fresh 12-byte nonce and a 16-byte tag. A fixed canonical authenticated header binds version, algorithm, KDF, iteration count and salt. Strict format/length/iteration validation precedes derivation. No secrets are logged.

`LocalPasswordStore.unlock(password, initialPasswords:)` opens an encrypted v2 primary, migrates valid v1 records, or creates an empty encrypted vault. Normal reads/writes require an unlocked key. `lock()` zeroes key bytes and invalidates asynchronous results. `changeMasterPassword(old,new)` stages and validates a new-salt vault, writes its encrypted backup, then commits the primary last. The primary determines the current password. Before the final rename fails, the original primary remains authoritative. Missing primary with backup or temporary data is an explicit error, never an empty vault. Authentication/format failures never overwrite a primary from backup.

All mutations serialize and are protected from application updates. Before commit, the original encoded primary is checked again; optimistic checks also compare UI snapshots. Remote rekeys invalidate an old session. Cloud changes arriving after the final check can still create provider conflict copies; distributed synchronization is not promised.

`SecureStorageService` delegates desktop unlock/lock/rekey and authenticates target directories using the current session password. A differing-password target is rejected without switching. Target libraries must already be v2; legacy targets must first be upgraded on their original device, avoiding any mutation of a target before authentication. Directory operations serialize with session unlock and rotation. Startup never writes plaintext. Active legacy preference lists are removed only after verified encrypted disk persistence. Unrelated old source folders and provider history remain untouched.

`AuthService` uses encrypted primary decryption as authority even with missing or stale preferences. Successful desktop unlock replaces the old fast SHA verifier with a public format marker. Only legacy migration checks the old SHA verifier. Password changes do not depend on updating password-specific settings, so a settings write failure cannot revoke access to the committed vault. Historical plaintext and old verifiers cannot be retroactively revoked; change the master password to invalidate old-password verifiers.

Tests cover ciphertext confidentiality/randomness, malformed and tampered data, wrong-password nonmutation, locked operations and invalidated unlocks, migration, missing-primary recovery refusal, stale cloud writes/rekeys, directory switching, password rotation and injected commit failures, config-less authentication and stale verifier rejection.

Clearing password records rewrites both main and backup as authenticated empty vaults under the current password; it never deletes the only authentication proof. Desktop login warns users to upgrade all synced devices and stop old clients writing the shared directory before encryption. Successful migration requires active plaintext preference removal and replacement of the active fast verifier. If preference writes fail, the operation reports failure and locks; the already-committed encrypted primary stays authoritative for retry.
