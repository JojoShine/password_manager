# Lockora 品牌更名与桌面应用内升级设计

日期：2026-11-04（Asia/Shanghai）  
阶段：用户已明确授权实施、GitHub 推送与 OSS 发布；代码已实施，发布验证进行中。

## 1. 已确认的目标

将现有桌面密码管理器更名为 **Lockora**，以 **3.1.0+5** 作为首个包含应用内升级能力的版本。沿用当前阿里云 OSS 分发，用户可以在应用中查看当前版本、检查新版本、阅读更新说明，并在确认后完成下载、验证、安装和重启。

自动升级的默认含义是“自动检查、用户点击后自动完成安装流程”。不会在编辑密码途中自动退出应用。已有 3.0.0 未包含升级程序，必须手动安装一次 Lockora；从 3.1.0 起支持后续应用内升级。

本次范围为 macOS、Windows 桌面端、配套浏览器扩展的名称，以及构建和发布流程。沿用上一轮已完成的存储目录选择、iCloud 文件共享、重复保存提示修复、连接恢复、安装引导和图标。

## 2. 当前项目事实

- Flutter 主项目位于 `password_manager/`，当前 `pubspec.yaml` 为 `3.0.0+4`。
- 配套扩展源码位于同级 `password_manager_browser/`，当前扩展版本为 `3.0.1`；应用通过 `assets/files/password_manager_browser.zip` 携带扩展。
- 应用尚未集成更新程序。当前生效的 GitHub Actions 工作流构建桌面产物，不生成更新订阅、不对更新包签名，也不上传 OSS。
- macOS 产品名为 `PasswordManager`，bundle identifier 为 `com.jojo.passwordmanager`；Windows 可执行文件、产品名为 `password_manager`，CompanyName 为 `com.example`。
- 默认桌面密码目录使用 `PasswordManager`，用户选择的目录记录在本机设置中。密码文件与应用程序分离。
- Windows 的 `path_provider_windows` 根据可执行文件资源中的 CompanyName / ProductName 计算应用支持目录，`shared_preferences_windows` 将设置保存在该目录。因此更改产品名会影响设置位置。
- 已有的实际下载地址使用 `https://tbtparent-me.oss-cn-hangzhou.aliyuncs.com/Download/`，本次在此基础上建立 Lockora 独立目录。
- 当前工作区有上一轮修改和既有未跟踪文档。本轮不覆盖、不回退，也不顺手提交这些内容。

## 3. 品牌名称与数据兼容

### 3.1 对用户可见的名称

- 默认应用标题、关于页名称、系统窗口和菜单、安装与卸载说明改为 `Lockora`。
- macOS 应用为 `Lockora.app`；Windows 可执行文件为 `Lockora.exe`，产品名和文件描述为 `Lockora`。
- 用户指定正式应用标识为 `me.tbtparent.lockora`。macOS 主应用及其测试目标同步使用新标识体系，`com.jojo.passwordmanager` 仅保留为旧版数据迁移来源。
- 浏览器扩展名称为 `Lockora 密码管理器`，工具栏名称为 `Lockora`，弹窗与页面提示同步改名。
- 第一版扩展更新到 `3.1.0` 并重新打包。以后只有扩展自身变化时才提升其版本，桌面版本与扩展版本无需始终相同。
- 当前盾牌与钥匙孔图标继续使用；不开展额外视觉重设计。
- 默认标题历史值“甜宝塔的密码管理工具”“密码管理工具”迁移为 Lockora；用户自定义标题保留。
- 内部 Dart 包名、Git 仓库名和与密码库相关的协议标识保持兼容，不为产品更名批量重写内部命名。

### 3.2 macOS 兼容

将主应用 bundle identifier 从 `com.jojo.passwordmanager` 改为用户指定的 `me.tbtparent.lockora`；后续所有 Lockora 自动升级版本保持这个新标识。测试目标使用 `me.tbtparent.lockora.RunnerTests`，签名与更新配置按新主应用标识生成。首次从旧版切换通过已确认的手动安装完成，不依赖更新程序跨标识替换应用。

在任何服务首次读取 SharedPreferences 之前迁移旧标识下的设置：

1. 新标识域已有有效应用设置时优先使用新设置，禁止旧域覆盖它；仅出现系统窗口等元数据不视为已完成应用迁移。
2. 新域没有应用设置时，通过系统偏好 API 读取 `com.jojo.passwordmanager` 的持久化应用设置。保留当前项目已有的旧沙盒偏好文件兼容读取路径，作为更早版本的回退来源。
3. 迁移主密码哈希、认证失败计数、锁定状态、主题、自定义标题及资源路径、默认／自定义密码库位置，包括 iCloud 目录选择。复制原始应用偏好键值，保持 Flutter 使用的键前缀。
4. 写入新域并回读核对后才记录迁移完成，再初始化存储和认证服务；遇到旧设置损坏、无法读取或保存失败时显示可重试错误，不自动进入首次设置或创建空库。
5. 原设置域、旧沙盒文件和密码数据保留；迁移可重试，重复启动不覆盖已完成迁移的新设置。不为迁移新建或重置主密码。

已有默认密码目录、自定义目录及 iCloud 密码文件保持原位置，不随应用标识修改自动搬动。Lockora 后续更新针对当前安装的 `me.tbtparent.lockora` 应用包进行，不替换密码数据目录。本次不更改 iOS／移动端标识；它们不在本轮桌面升级范围内。

首次安装说明要求用户退出旧版、将 Lockora 放入“应用程序”，确认数据正常后再移除旧应用程序。安装代码不自动删除可能仍被用户使用的旧 `PasswordManager.app`。

### 3.3 Windows 兼容

保留现有 CompanyName，仅把 ProductName 改为 Lockora。首次启动时，在任何服务首次调用 SharedPreferences 之前执行设置迁移，包括 `WebStorageService.initialize()` 之前。

迁移源是现有 `%APPDATA%\com.example\password_manager\shared_preferences.json`，目标是新产品名对应的应用支持目录。流程如下：

1. 目标存在有效设置时使用目标，不用旧设置覆盖它。
2. 目标不存在而旧文件存在时，校验 JSON 对象、复制到临时文件并核对内容，再原子提交目标文件。
3. 原文件始终保留。目标文件损坏，或旧文件存在但读取／复制失败时，显示可重试的启动错误，不自动把已有用户当成首次使用者。
4. 两边都不存在才进入真正的首次设置流程。迁移完成后重新读取设置，再初始化密码存储和认证服务。

复制完整设置文件，保留主密码哈希、失败次数、锁定时长、主题、自定义标题和已选择的密码库路径；日志不输出这些内容。桌面密码库仍使用原目录，不进行重命名或自动合并。

## 4. 版本与发布记录

- 桌面版本唯一来源为 `pubspec.yaml` 的 `version: 3.1.0+5`；运行时通过 `package_info_plus` 显示实际安装版本，不以 AppSettings 中的历史字段判断更新。
- 用户看到的版本为 `3.1.0`，详情可显示构建号 `5`。每次正式发布，语义版本和构建号都必须高于上一正式版本。
- Git 标签格式为 `v3.1.0`，必须与 pubspec 的公开版本一致；构建号由 pubspec 取得，不从当前时间或 CI 运行序号临时推算。
- macOS 更新比较使用递增的 `CFBundleVersion`；Windows 使用数值版本 `3.1.0.5`，显示版本为 `3.1.0`。两个平台分别生成订阅，避免版本比较规则混用。
- `CHANGELOG.md` 中的对应版本条目作为更新说明来源，发布工具生成该版本的静态说明页面。找不到对应条目时拒绝正式发布。
- 维护已发布版本与安装包，允许用户下载历史版本作人工恢复；客户端不自动降级。

## 5. 用户流程

### 5.1 设置入口

在“设置”增加“版本与更新”：显示当前版本与构建号、“检查更新”按钮和“自动检查更新”开关。开关默认开启；关闭后仍允许手动检查。

检查新版本、展示最新版本和更新说明、下载进度、安装确认由平台更新窗口承担，不另写一套与原生更新程序竞争的下载／安装界面。应用内显示的后台状态与原生结果保持一致，不在请求失败时显示“已是最新版本”。

### 5.2 自动检查

正常启动并显示界面后进行一次不阻塞启动的后台检查；同一设备在成功检查后的 24 小时内不重复自动检查。应用持续运行时按原生更新机制执行每日检查。自动与手动检查合并并发请求，手动检查不受每日间隔限制。

检查失败不阻止登录、密码库读写或扩展连接，也不反复弹出错误；手动检查失败时在更新界面给出重试提示。自动发现更新时可提示用户，用户选择稍后更新后不立即重复打扰。

### 5.3 安装和重启

用户确认更新后，由原生程序下载并验证包。安装前确认本地密码写入、导入和设置迁移已结束，且没有打开的密码编辑等业务弹窗；不满足条件时保留当前运行状态，让用户先完成操作再继续。

确认退出前锁定密码库、清除内存会话并关闭本机扩展服务。安装完成后重启进入正常的锁定／解锁流程；不把明文主密码或解锁状态传给安装器。浏览器扩展通过已有配置刷新机制重新连接。

## 6. 更新实现边界

采用 Flutter 中的一个小型更新服务负责配置、用户设置和主动检查调用，macOS 接入 Sparkle 2，Windows 接入支持 Ed25519 的 WinSparkle 0.9 或以上版本。具体依赖版本与校验值在实施计划和锁文件中固定；不使用只支持旧 DSA 的封装替代已确认的签名方案。

平台更新程序负责版本比较、下载、签名验证、安装器调度和重新启动；应用不自行生成覆盖安装的 shell / PowerShell 脚本。通过窄的平台桥接传递检查命令、必要结果和“当前可否退出安装”的状态，不建立通用插件框架。

macOS 使用完整 `.app` 的 ZIP 作为更新载体，保留符号链接与执行权限。Windows 从 3.1.0 起采用稳定 AppId、按用户安装的 Inno Setup 安装包，默认安装于 `%LOCALAPPDATA%\Programs\Lockora`，整个运行目录和依赖一起升级。旧版 ZIP 用户首次运行 Lockora 安装包完成过渡；本轮不承诺对任意旧便携目录进行原地自更新。

开发环境和未配置正式更新源／公钥的构建明确显示更新功能尚未配置，不将配置缺失当成“最新版”，也不以测试密钥对外发布。正式构建必须通过配置与签名检查。

## 7. OSS 目录与订阅格式

采用现有 OSS 域名，通过 HTTPS 提供以下资源：

```text
Download/lockora/
  updates/stable/macos.xml
  updates/stable/windows.xml
  releases/3.1.0/
    Lockora-3.1.0-macos.zip
    Lockora-3.1.0-windows-setup.exe
    Lockora-3.1.0-browser.zip
    release-notes.html
    checksums.sha256
```

更新订阅为平台各自的 RSS appcast；不额外维护一份手工填写的 latest.json。版本号、构建号、最低系统版本、包长度、HTTPS 下载地址、说明地址和 Ed25519 签名均由同一次发布的产物生成。

macOS 包提供当前受支持的桌面架构，发布工具校验实际二进制架构与订阅匹配；Windows 首次支持当前的 x64 构建，订阅明确标记为 `windows-x64`。不向不支持的平台或系统版本提供不可安装的更新。

版本目录不可覆盖；订阅文件才是可变的稳定入口。安装包与更新说明使用长缓存，订阅使用短缓存并允许重新验证，防止用户长期读取旧版本入口。

## 8. 信任与签名

每个平台使用其原生工具生成并管理 Ed25519 更新签名密钥；客户端只包含对应公钥。私钥不写入源码、日志、安装包或 OSS，并通过发布环境的密钥存储提供给签名步骤。

所有正式更新包在发布前签名，客户端拒绝缺失或无效签名的包。HTTPS、SHA-256 文件校验和与 Ed25519 各司其职：下载传输、发布产物核对、客户端验证发布者，不能只用 SHA-256 替代签名。

推荐 macOS 对外分发配置 Developer ID 签名和公证，并验证 Sparkle helper 的签名；Windows 推荐使用代码签名证书签署 EXE 与安装包。平台代码签名和更新包签名是不同配置。Ed25519 更新包签名是启用正式自动升级的硬性要求；平台证书按已有发行条件配置，不自动购买证书。缺少平台证书时明确记录该状态，并以真实安装升级验证作为分发依据，不声称已经完成系统签名或公证。缺少更新签名材料时，发布任务不得更新公开订阅。

密钥轮换按 Sparkle / WinSparkle 支持的兼容路径处理，不能直接替换公钥并期望所有旧客户端继续升级；本轮不建设密钥管理后台。

## 9. 构建和发布流程

正式发布继续由 GitHub Actions 构建，但以受保护的发布环境控制 OSS 写入。推送匹配版本的标签准备候选产物；人工启动的构建默认只上传 CI 产物，不触发公开升级。

1. 检查标签、pubspec、构建号、变更日志和更新配置，运行相关测试。
2. 分别构建 macOS 与 Windows，校验 Lockora 名称、身份兼容配置和内置扩展版本，生成标准分发包。
3. 按已配置的证书执行平台代码签名／公证，并执行必需的更新包签名；生成 appcast、更新说明、校验文件。
4. 两个平台均通过验证后，先上传不可变版本目录，再核对 OSS 上的文件大小与校验和。
5. 经发布环境批准，最后更新两个平台的稳定订阅；两个对象无法作为一次 OSS 事务提交，发布工具需要检查两边结果并支持重试。在短暂不一致期间，只会有一个平台先看到新版，不会引用未上传的包。
6. 任一前置步骤失败都不修改稳定订阅；保留候选产物及清晰的失败信息供修复。

首次生产发布前需配置 OSS 发布身份、更新签名材料，并确认平台代码签名／公证的发行状态。配置说明记录所需变量和 Secret 名称，不要求用户在聊天中粘贴私钥或 OSS 凭据。

GitHub Releases 可以后续加入镜像分发；本轮不将它设为客户端必须可访问的更新源，不自动修改远端仓库名或推送发布。

## 10. 失败与恢复

| 情况 | 预期行为 |
| --- | --- |
| 断网、订阅超时或 404 | 继续使用当前版本；手动检查显示可重试错误 |
| 订阅格式不合法或无适用架构 | 不安装；区分检查失败与没有兼容更新 |
| 旧版本／相同版本订阅 | 不自动降级或重复安装 |
| 包损坏、缺失或签名错误 | 不退出、不运行安装器、不替换当前程序 |
| 用户取消下载或选择稍后安装 | 保持密码库和当前程序可用 |
| 存在未完成写入或编辑弹窗 | 不强制退出；提示先完成操作 |
| macOS 从只读磁盘映像运行 | 解释需先安装到可写应用目录；不尝试绕过权限 |
| 磁盘空间不足、安装权限不足 | 使用原生错误处理；不得删除密码目录作为恢复手段 |
| 安装过程被中断 | 提供已签名完整安装包用于修复；不承诺所有系统故障下均能原子回滚 |
| 新版业务功能发布后出现问题 | 暂停公开订阅，保留历史包；对已升级用户发布更高构建号的修复版本 |

所有安装与卸载脚本明确不删除本地密码库、自定义目录、iCloud 文件或主密码设置。本轮不改变密码库文件格式和现有明文存储边界。

## 11. 验收与证据

### 应用与迁移

- 系统、关于页、默认标题、桌面产物及扩展均显示 Lockora；用户自定义标题保留。
- macOS 应用包和测试目标使用 `me.tbtparent.lockora` 标识体系；后续更新包身份一致。
- macOS 迁移测试覆盖旧偏好域、历史沙盒偏好、新域已有有效设置、新域只有系统元数据、源损坏、写入失败和重复启动。旧主密码、失败计数、设置、默认库和 iCloud 目录在首次手动安装后保持可用；迁移失败不能表现成首次使用或空密码库。
- Windows 测试覆盖旧设置迁移、目标已存在、源损坏、写入失败和重复启动；失败不能表现成空库或首次使用。
- 上一轮 Flutter 76 项、扩展 30 项测试作为当前回归基线；新增测试不替代已有回归。

### 更新功能

- 使用独立测试源与测试密钥完成 3.1.0 到更高构建的真实下载、校验、安装、重启、重新解锁和扩展重连。
- 覆盖没有新版本、断网、订阅格式错误、错误架构、同版本、自动检查关闭、并发检查、错误签名和安装取消。
- 编辑弹窗打开及写入未完成时不退出；完成操作后可安装。
- 更新前后主密码设置、密码记录和自定义存储位置保持一致。
- macOS、Windows 都需要对应系统上的安装验证；只通过 macOS 构建不能报告 Windows 更新链路已经验证。

### 发布工具

- 标签与版本不匹配、构建号不递增、缺少说明／公钥／签名材料、产物缺失时必须失败。
- 测试上传顺序和失败场景：稳定订阅不得先于完整安装包公开，不得指向测试包。
- 验证归档内包含本次扩展文件与正确的 Lockora 可执行文件，macOS 打包保留符号链接与权限。
- 发布验证需要实际观察公开订阅指向的签名产物，单纯生成本地 XML 不算上线成功。
